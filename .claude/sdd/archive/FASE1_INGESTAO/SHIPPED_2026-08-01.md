## Summary

Primeira fatia executável da plataforma Zero-Touch Data Mesh: uma camada de ingestão que captura cotações reais da B3 (via brapi.dev) e fontes corporativas simuladas (CRM Lost Sales, telemetria de infra, logs de uso) através de Kafka e Airflow 3.0, valida cada registro contra um contrato de dados versionado e promove os válidos a tabelas Delta no Bronze — isolando falhas numa DLQ unificada sem interromper o fluxo. Entrega o alicerce técnico (contratos, DAGs, producers) sobre o qual as Fases 2-5 (self-healing, FinOps, RAG, entrega via Microsoft Graph) serão construídas, e serve como a primeira peça concreta e demonstrável do portfólio descrito em `context.md`.

## Lessons Learned

### Process

- Validar contra infraestrutura real assim que possível expõe bugs que revisão de código, contract gates e testes unitários com mocks não pegam: 4 dos 8 problemas encontrados nesta feature só apareceram rodando de fato contra Airflow 3.0 e Kafka reais, apesar de o BUILD_REPORT já mostrar 100% dos testes unitários passando antes disso.
- Quando uma validação esbarra numa limitação de ambiente (CPU do Docker Desktop, não do código), parar e apresentar as opções ao usuário — em vez de insistir indefinidamente ou fingir que passou — foi a decisão certa; documentar a limitação honestamente no BUILD_REPORT preserva a confiabilidade do relatório.

### Technical

- APIs de providers do Airflow mudam de forma sutil entre versões, mesmo quando um padrão da KB parece aplicável: `AwaitMessageTriggerFunctionSensor` existe e é um sensor Kafka legítimo, mas exige um argumento obrigatório (`event_triggered_function`) que não aparecia no resumo do padrão consultado. Usar `inspect.signature()` dentro do container real foi mais confiável do que confiar apenas na KB.
- Dependências implícitas em DAGs TaskFlow (`sensor >> validate_and_promote(consume())`) podem deixar uma task solta se o resultado da task interna não for capturado numa variável antes de encadear — o bug em `dag_ingest_kafka_market.py` (consume_microbatch sem depender do sensor) é uma pegadinha fácil de repetir e só apareceu observando o grafo de dependências real de uma DAG run.
- Usar `deltalake` (delta-rs) para escrever o Bronze sem provisionar um cluster Spark foi a decisão certa para uma fase de ingestão numa conta cloud trial: validado escrevendo/lendo tabelas Delta reais sem nenhum custo de cluster.

### Communication

- Perguntar ao usuário, ainda no brainstorm, qual fonte real usar (brapi.dev) e qual ambiente de execução (cloud trial vs. local) evitou retrabalho de arquitetura mais tarde — a escolha de Approach B (Airflow micro-batch) só fez sentido depois de saber que o ambiente-alvo seria uma conta trial, não um cluster dedicado.
- Ao encontrar o limite de CPU do ambiente local, apresentar 3 opções claras ao usuário (aceitar a validação já obtida / aumentar recursos do Docker Desktop / desistir da checagem específica) em vez de decidir sozinho manteve o usuário no controle da troca custo-benefício entre tempo gasto e confiança adicional.

### Tools & Libraries

- `deltalake` (delta-rs) — biblioteca leve, sem dependência de JVM/Spark, ideal para tasks Python simples lerem/escreverem Delta Lake diretamente.
- Baixar o `docker-compose.yaml` oficial da Apache Airflow como ponto de partida (em vez de escrever um do zero) garantiu fidelidade à arquitetura real do Airflow 3.0 (apiserver/scheduler/dag-processor/triggerer como componentes separados) — algo fácil de errar escrevendo de memória, como o próprio Pattern 2 do DESIGN demonstrou ao usar um sensor com API incorreta.

## Recommendations for Future Work

| Area | Recommendation |
|------|----------------|
| Ambiente de execução | Antes de tentar de novo uma DAG run completa via scheduler, provisionar a conta cloud trial real (Confluent Cloud + Astronomer/Databricks trial) com CPU dedicada — o Docker Desktop local não sustentou o scheduler+triggerer do Airflow 3.0 sob carga |
| Cobertura de testes | Automatizar a validação de infraestrutura real feita manualmente aqui (produção Kafka real, DAGs importando sem erro) como parte de um pipeline de CI que sobe o `docker-compose.local.yml`, já que ela encontrou bugs que os testes unitários mockados não pegam |
| Fase 2 (próxima) | Reaproveitar o contrato de dados YAML e a tabela `bronze_dlq` unificada já criados aqui — o agente de self-healing da Fase 2 deve consumir essa tabela diretamente, sem precisar de um novo formato |
| AT-003 (falha de rede) | Teste automatizado já cobre o caminho de retry/backoff; falta um teste de carga/caos mais realista (ex: `toxiproxy`) quando a fonte real B3 estiver em produção |
