## Summary

Segunda fatia executável da plataforma Zero-Touch Data Mesh: um pipeline PySpark que promove os dados validados do Bronze (Fase 1) até a Silver no Databricks, e um agente de self-healing que escuta falhas de contrato (`bronze_dlq`) e de execução (Airflow), diagnostica a causa raiz via Claude com saída estruturada, passa por duas camadas de guardrail determinísticas (allowlist de arquivos + padrões perigosos), e só então abre um Pull Request no GitHub para revisão humana — nunca mergeando sozinho. Fecha o primeiro ciclo real de resiliência da plataforma: dado ruim não trava o pipeline, vira uma proposta de correção rastreável.

## Lessons Learned

### Process

- Repetir o roteiro de validação real da Fase 1 (Docker + Airflow de verdade) direto na Fase 2 valeu a pena de novo: achou um bug (import pesado do `anthropic`) que nenhum teste unitário isolado detectaria, porque só se manifesta no *parse* do DAG, não na execução da função em si.
- Verificar a API de um operator/provider por introspecção real (`inspect.signature()`) antes de confiar no código do DESIGN compensou: desta vez o `DatabricksRunNowOperator` bateu exatamente com o que eu tinha documentado — nem toda validação encontra bug, mas a confiança ganha em achar "nenhum problema" só é real quando a checagem foi de fato feita.

### Technical

- Import pesado no topo de um módulo Python pode quebrar o parse de um DAG do Airflow mesmo sem nenhum erro de lógica: o `anthropic` SDK constrói uma árvore grande de modelos Pydantic na importação, e isso sozinho passou do timeout padrão de 30s que o Airflow usa pra descobrir DAGs. A regra geral "evite imports pesados no topo do arquivo de DAG" (que a própria mensagem de erro do Airflow cita) é mais literal do que parece — vale para qualquer SDK com muito código gerado em tipos, não só bibliotecas óbvias como pandas/numpy.
- Pesquisar a documentação oficial durante o Design (não só confiar em conhecimento prévio) pegou uma mudança real de produto: "Databricks Community Edition" tinha sido descontinuada e substituída pelo "Free Edition" — desenhar em cima do produto errado teria sido descoberto tarde demais, só na hora de provisionar.
- Coluna aditiva (`detected_at`) em uma tabela Delta já shipped é uma forma segura de estender um contrato sem quebrar leitores antigos — confirmado rodando de novo a suíte de testes da Fase 1 depois da mudança.

### Communication

- Quando o usuário pediu guardrails "desde já" e escopo mais amplo do que eu tinha sugerido no YAGNI inicial, pedir esclarecimento específico (que tipo de guardrail, até onde diagnosticar) em vez de assumir uma interpretação evitou desenhar a coisa errada.
- Perguntar "continue" de forma ambígua do usuário foi interpretado como "siga o padrão que já funcionou" (validar antes de dar ship) — em caso de ambiguidade real, documentar a interpretação escolhida (como fiz aqui) permite ao usuário corrigir se a leitura estiver errada.

### Tools & Libraries

- `anthropic` SDK — poderoso para saída estruturada via tool use, mas caro de importar; isolar o import dentro da função que o usa é obrigatório em contextos com timeout de parse (Airflow) ou de cold start (serverless).
- Reaproveitar o `docker-compose.local.yml` da Fase 1 (só adicionando os novos requirements e volumes de DAG) foi muito mais rápido do que montar um stack novo do zero.

## Recommendations for Future Work

| Area | Recommendation |
|------|----------------|
| Databricks Free Edition | Provisionar o workspace real e rodar `bronze_to_silver.py` de fato — a lógica de MERGE nunca foi exercitada contra um cluster Spark real |
| Self-healing fim a fim | Testar o fluxo completo com `ANTHROPIC_API_KEY` e um token do GitHub reais, contra um repositório de teste (não o AutoMesh direto) antes de habilitar em produção |
| Cobertura retroativa | Retrofitar o `on_failure_callback` nos 3 DAGs da Fase 1 (Decision 3 do DESIGN deixou isso como fast-follow deliberado) |
