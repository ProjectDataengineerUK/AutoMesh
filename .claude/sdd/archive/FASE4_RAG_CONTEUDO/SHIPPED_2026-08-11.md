## Summary

Quarta fatia executável da plataforma Zero-Touch Data Mesh: um motor RAG corporativo que ingere documentos reais do SharePoint via Microsoft Graph (delta query, OAuth2 app-only), indexa via Databricks Vector Search (Delta Sync Index) e responde com retrieval híbrido (semântico+lexical nativo) mais rerank via Claude — e uma fábrica de conteúdo que cruza os outliers de mercado da Fase 3 com esse conhecimento documental, gera rascunhos de relatório e só deixa um rascunho virar Pull Request depois de passar por um gate RAGAS bloqueante (faithfulness + answer relevancy). Fecha o terceiro ciclo de reaproveitamento do mecanismo de guardrails+PR construído na Fase 2 — agora falhas de pipeline, decisões de ML/custo, e geração de conteúdo passam pelo mesmo funil de revisão humana, com uma extensão pontual (`resolve_diagnosis()`) que preserva a fidelidade entre o texto avaliado pelo RAGAS e o texto que efetivamente chega ao PR.

## What Was Built

### Components

| Component | Description |
|-----------|-------------|
| SharePoint Ingestion | OAuth2 app-only (MSAL) + Graph delta query → chunking → contrato → Bronze (reaproveita `bronze_writer`/`contract_validator` da Fase 1 sem duplicar lógica) |
| Vector Index | Delta Sync Index (Databricks Vector Search) sincronizado automaticamente a partir de `bronze.sharepoint_documents`; busca híbrida nativa (`query_type="HYBRID"`) |
| Retrieval | Busca híbrida + rerank por relevância via Claude (tool call), sem reranker/infra dedicada |
| Content Factory | Cruza outliers (`gold.market_insights`, Fase 3) com o contexto recuperado, gera rascunho via Claude, aplica NeMo Guardrails (output rail) e avalia RAGAS (faithfulness + answer relevancy) como gate bloqueante |
| RAG Guardrails | NeMo Guardrails isolado em `pipelines/rag/`, sem tocar no guardrail determinístico (allowlist + padrões perigosos) da Fase 2 |
| Self-Healing (reaproveitado) | `resolve_diagnosis()` — eventos `content_generation` pulam a chamada ao LLM diagnostician e reconstroem o `Diagnosis` diretamente do payload já aprovado pelo RAGAS, preservando fidelidade byte-a-byte entre o texto avaliado e o corpo do PR |

## Lessons Learned

### Process

- Delegar formalmente 6 dos 31 arquivos para agentes especialistas no DESIGN e depois construir todos os 31 diretamente a partir dos padrões já totalmente especificados (em vez de spawnar ~8 subagentes) não custou qualidade — os padrões do DESIGN já eram copy-paste-ready o suficiente para isso, e a verificação incremental (ruff + pytest por arquivo) pegou os dois desvios reais que ocorreram de qualquer forma. Delegação formal só compensa quando o padrão ainda não está totalmente especificado.
- Repetir pela quarta vez o roteiro "reaproveitar o pipeline de guardrails+PR da Fase 2 em vez de duplicar" continua sendo a decisão de maior alavancagem do projeto: dos 31 arquivos desta fase, só 5 tocaram o self-healing existente, e 4 desses 5 foram diffs de poucas linhas.

### Technical

- A precisão importa mais que a consistência de padrão: `resolve_diagnosis()` deliberadamente **quebra** o precedente "zero mudança de lógica" que as Fases 2-3 estabeleceram, porque aqui havia um requisito novo que as fases anteriores não tinham — preservar fidelidade byte-a-byte entre um conteúdo já avaliado por um gate de qualidade (RAGAS) e o que vira PR. Seguir o precedente cegamente teria introduzido um bug sutil (o LLM "reformatando" o rascunho podia invalidar silenciosamente o score já calculado).
- O critério "lazy import só para SDKs pesados" precisa ser aplicado biblioteca a biblioteca, não como regra geral: `msal` foi inicialmente importado como lazy (copiando o padrão usado para `anthropic`/`mlflow`/`databricks-vectorsearch`/`nemoguardrails`), mas isso quebrou o `unittest.mock.patch` do teste — `msal` não tem a árvore de import pesada que justifica o padrão, e o próprio DESIGN já mostrava isso corretamente como import de topo. O teste automatizado pegou a divergência antes de virar problema de produção.
- Reaproveitar `contract_validator.py`/`bronze_writer.py` da Fase 1 quase de graça (um parâmetro opcional `contracts_dir`) significou que a DLQ de `sharepoint_documents` já cai automaticamente no mesmo `dag_self_healing_diagnose` que processa a DLQ de `b3_quotes`/`crm_lost_sales` desde a Fase 1 — zero integração nova, zero teste novo necessário para essa parte.

### Communication

- Documentar explicitamente que dois riscos de infraestrutura (Vector Search/Unity Catalog no Free Edition, tenant Microsoft 365 Developer) seguem **não validados** — em vez de deixar implícito ou tentar simular localmente algo que não dá para simular — manteve o Build Report honesto sobre o que de fato foi testado (mocks) versus o que precisa de uma sessão de validação real dedicada, mesmo padrão que a Fase 3 já havia estabelecido com o MLflow/Databricks.

### Tools & Libraries

- `databricks-vectorsearch` com `query_type="HYBRID"` elimina a necessidade de implementar e manter um índice lexical (BM25) próprio — mesma filosofia de "não reconstruir o que a plataforma já oferece nativamente" que guiou a escolha de Delta Sync Index em vez de um job de embedding manual.
- Reaproveitar a API da Anthropic (já em uso desde a Fase 2) tanto para o rerank quanto para o RAGAS evaluator LLM (via `langchain-anthropic`) evitou introduzir um segundo provedor de LLM/segredo só para essas duas peças.
